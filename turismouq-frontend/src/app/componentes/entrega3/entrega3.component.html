Arquitectura Transaccional Atómica con Rollback Parcial

Procedimiento almacenado PKG_TURISMO_UQ.sp_registrar_reserva_con_pago. Crea la reserva, fija un SAVEPOINT sp_reserva_creada y procesa el cobro bancario. Si el pago falla, la transacción no se aborta por completo: revierte solo el cobro al SAVEPOINT y preserva la reserva en estado PENDIENTE, cumpliendo el principio ACID sin pérdida de reservas.

Mecánica Interna PL/SQL:
  1. Se validó la disponibilidad de fechas con función fn_verificar_disponibilidad.
  2. Se insertó la cabecera en RESERVA y se ejecutó SAVEPOINT sp_reserva_creada;.
  3. El cobro fue exitoso: se insertó en PAGO, la reserva pasó a CONFIRMADA y se ejecutó COMMIT;.
  4. Falló el pago: la excepción capturada ejecutó ROLLBACK TO SAVEPOINT sp_reserva_creada;, preservó la reserva en estado PENDIENTE y persistió con COMMIT; para no perder el turno del cliente.

Control de Concurrencia Pesimista: SELECT ... FOR UPDATE WAIT 5

Procedimiento sp_reserva_concurrente_for_update en 02_concurrencia_bloqueos.sql. Evita la sobreventa de alojamientos (race condition) bloqueando la fila de la habitación a nivel de transacción exclusiva. Si otra sesión intenta reservar al mismo tiempo, espera ordenadamente hasta 5 segundos antes de abortar de forma limpia con ORA-30006.

Protocolo de Demostración Multisesión en Oracle XE

2 Sesiones Concurrentes
Terminal 1 · Sesión A

Transacción Adquirente

Ejecuta la reserva adquiriendo el cerrojo exclusivo de fila en la habitación #1:

-- Sesión A (SQL*Plus / DBeaver)
VARIABLE v_res NUMBER;
VARIABLE v_msg VARCHAR2(300);

EXEC sp_reserva_concurrente_for_update(
  p_id_habitacion   => 1,
  p_id_cliente      => 1,
  p_fecha_checkin   => DATE '2026-11-01',
  p_fecha_checkout  => DATE '2026-11-05',
  p_num_huespedes   => 2,
  p_id_reserva      => :v_res,
  p_mensaje         => :v_msg
);

-- Estado: TX Lock exclusiva adquirida.
-- NO se ha ejecutado COMMIT todavÃ­a.
🔒
Fila HABITACION #1 Bloqueada Modo: Exclusive Row Lock (TX Lock)
Terminal 2 · Sesión B

Transacción Competidora

Intenta reservar la misma habitación #1 en las mismas fechas inmediatamente después:

-- Sesión B (Segunda terminal concurrente)
VARIABLE v_res2 NUMBER;
VARIABLE v_msg2 VARCHAR2(300);

EXEC sp_reserva_concurrente_for_update(
  p_id_habitacion   => 1,
  p_id_cliente      => 2,
  p_fecha_checkin   => DATE '2026-11-02',
  p_fecha_checkout  => DATE '2026-11-04',
  p_num_huespedes   => 1,
  p_id_reserva      => :v_res2,
  p_mensaje         => :v_msg2
);

-- Comportamiento:
-- Espera en cola hasta 5 segundos (WAIT 5).
Caso A (Sesión 1 hace COMMIT): Sesión 2 detecta habitación no disponible y devuelve ORA-20002 controlada sin duplicidad.
Caso B (Sesión 1 retiene > 5 seg): Sesión 2 captura ORA-30006 y aborta limpiamente sin congelar el hilo de la aplicación.

¿Por qué SELECT ... FOR UPDATE WAIT 5 frente a otras alternativas?

Estrategia Bloqueo en BD Riesgo de Bloqueo Indefinido Manejo en la Aplicación
Sin Bloqueo Ninguno Ninguno Grave: Sobreventa y solapamiento de habitaciones
FOR UPDATE (Sin WAIT) Exclusivo Fila Muy Alto (Hilos congelados indefinidamente) El usuario queda esperando sin respuesta
FOR UPDATE NOWAIT Exclusivo Fila Ninguno Falla inmediatamente al menor milisegundo de competencia
FOR UPDATE WAIT 5 (Implementada) Exclusivo Fila Cero (Timeout garantizado a 5 seg) Óptimo: reintenta brevemente y responde de forma elegante
